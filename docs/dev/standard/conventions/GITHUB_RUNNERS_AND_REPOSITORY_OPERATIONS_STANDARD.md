# Стандарт управления GitHub runners и репозиториями

> Общий стандарт для проектов, где AI-агенты, GitHub Actions и сервер
> автоматизации работают с self-hosted runners и Git-репозиториями.

## 1. Назначение

Стандарт разделяет три разные задачи:

1. наблюдение за состоянием GitHub и локального сервера;
2. безопасное исправление ограниченных неисправностей;
3. опасные операции, которые всегда требуют подтверждения человека.

Мониторинг не должен незаметно превращаться в произвольное удалённое
управление машиной.

## 2. Что является источником состояния

Для каждого runner проверяются оба источника:

- GitHub API: runner существует, `status`, `busy`, репозиторий и метки;
- локальная машина: Windows service или другой зарегистрированный процесс,
  его состояние и возраст последней проверки.

Для каждого репозитория проверяются:

- путь и текущая ветка;
- `origin` и upstream;
- локальные изменения;
- `ahead` и `behind` после fetch;
- состояние `OK`, `DIRTY`, `NEED_PULL`, `NEED_PUSH`, `DIVERGED`,
  `NO_UPSTREAM`, `FETCH_FAILED` или `UNKNOWN`.

Один результат проверки должен сохраняться в машинном JSON и в журнале
операций. Dashboard и уведомления читают этот результат, а не запускают
собственную копию проверки.

## 3. Разрешённые автоматические действия

По расписанию без подтверждения человека разрешены только:

- чтение GitHub API и локального состояния;
- запись журналов;
- запуск остановленного runner-сервиса, если это явно включено настройкой;
- fast-forward pull репозитория, только если он чистый, не имеет локальных
  коммитов впереди и не расходится с upstream.

Автоматический pull должен иметь фичефлаг и режим `dry-run`. Ошибка одной
машины или репозитория не должна скрываться и не должна приводить к работе
с другими объектами вне выбранной области.

## 4. Операции только с подтверждением

Следующие действия нельзя выполнять молча из watchdog, планировщика или
агента:

- stop, restart, reset или reconfigure runner;
- регистрация или удаление runner;
- удаление репозитория, ветки или worktree;
- push в GitHub;
- merge в защищённую ветку;
- force-push или переписывание истории;
- выполнение произвольной команды на сервере.

Для таких действий нужны авторизованный оператор, явное подтверждение,
предварительный просмотр (`dry-run`, где применимо) и запись в журнале:
кто, когда, над каким объектом и с каким результатом выполнил действие.

## 5. Контракт управления

Управляющий модуль должен разделять операции:

```text
status   — только чтение состояния
logs     — только чтение журналов
start    — запуск конкретного runner-сервиса
stop     — остановка конкретного runner-сервиса
restart  — остановка и запуск конкретного runner-сервиса
pull     — безопасный fast-forward pull выбранного репозитория
```

Каждый ответ должен содержать `action`, `target`, `before`, `after`,
`ok`, `error` и `operator_confirmation`.

Имена runner-сервисов, репозиториев, пути, интервалы и таймауты задаются
конфигурацией или реестром. Их нельзя зашивать в коде.

## 6. Разделение управления и исполнения

### 6.1. Роли узлов

Контроллер и узел исполнения — разные роли:

- контроллер принимает команду, планирует операцию, проверяет и фиксирует
  требуемое подтверждение и отвечает за результат;
- узел исполнения — машина, на которой работа фактически выполняется.

Совпадение обеих ролей на одной машине является нормальным, а не временным
случаем. Если работа ведётся на ноутбуке, её не следует переносить на сервер
только потому, что сервер автоматизации координирует предусмотренные операции
и наблюдает GitHub Actions. Управляющий узел и узел исполнения — не одно и то
же.

Для рабочего пространства каждого узла объявляется одна роль:

- активная разработка;
- зеркало;
- только раннер;
- отключён.

### 6.2. Проверки до и после отправки изменений

Проверки до и после `push` (отправки изменений) нельзя смешивать:

- **До `push`.** Проверяемое состояние существует только в рабочем каталоге
  конкретной машины. Раннер GitHub Actions получает отдельную копию
  отправленного коммита и этих изменений не видит. Такая проверка выполняется
  только на машине, где изменения лежат.
- **После `push`.** Источником состояния является коммит, одинаковый для всех
  машин. Место исполнения выбирается по назначению задачи.

### 6.3. Выбор места исполнения

| Условие | Где исполнять |
|---------|---------------|
| Задача затрагивает неотправленные изменения | Только тот узел, где они лежат |
| Задача требует macOS или окружения владельца | Узел на macOS |
| Задача фоновая, ночная или должна пережить закрытый ноутбук | Постоянно работающий узел |
| Задача обязана подтвердить переносимость | Обе машины |
| Во всех остальных случаях | Раннер GitHub |

Последняя строка основана на измерении: пилот 26.08.2026 на репозитории
qai-fabric показал 204 секунды на своём узле с Windows против 65 секунд на
`ubuntu-latest`, то есть свой узел оказался втрое медленнее. При этом он делит
ресурсы между семью репозиториями. Свой раннер экономит оплачиваемые минуты,
но платит временем ожидания, поэтому выбор между ним и раннером GitHub должен
быть осознанным: свой раннер не всегда лучше.

### 6.4. Недоступность узла

Если требуемый узел недоступен, поведение зависит от класса задачи:

- для задачи класса «до отправки изменений» обязателен явный отказ. Ожидание
  и перенос запрещены: неотправленных изменений на другой машине не
  существует, а перенос проверил бы чужое состояние под видом исходного;
- для задачи класса «после отправки изменений» допустим перенос на другой
  узел, потому что источником состояния является коммит.

В обоих случаях молчаливый перенос запрещён. Инициатор должен видеть, на каком
именно узле фактически выполнялась задача.

### 6.5. Граница доверия

Недоверенный запрос на слияние из внешней копии репозитория нельзя исполнять
на собственных машинах. Сегодня это требование соблюдается случайно, потому
что все репозитории парка закрытые. Закрытость текущего парка не является
защитой для будущего публичного репозитория. Правило обязательно уже сейчас
и должно быть обеспечено до появления первого публичного репозитория, а не
после него.

## 7. Мониторинг GitHub Actions

Если проект следит не только за runner, но и за выполнением workflows,
проверяются:

- последний запуск workflow;
- `status` и `conclusion`;
- ветка и commit;
- длительность и возраст запуска;
- очередь, зависшие и повторно падающие запуски.

Состояние runner (`online/offline`) и состояние workflow (`queued/
in_progress/success/failure`) нельзя смешивать в одно поле.

## 8. Минимальные проверки реализации

Для каждой новой операции обязательны:

- unit-тест нормального результата;
- тест отказа GitHub API или локального сервиса;
- тест запрета операции без подтверждения;
- тест режима `dry-run`;
- тест, что push, force-push и merge недостижимы из watchdog;
- API или CLI-тест с проверкой JSON-контракта;
- проверка журналирования успешной и неуспешной операции.

Ручная проверка на сервере выполняется отдельно от unit-тестов и не должна
менять runner или репозиторий без явного указания оператора.

## 9. Правило для AI-агента

Перед изменением проекта агент:

1. проверяет состояние репозитория и текущую ветку;
2. читает свежий отчёт мониторинга, если он доступен;
3. не трогает dirty-репозиторий и чужую ветку;
4. после изменения запускает тесты и структурный валидатор;
5. делает commit только в своей ветке;
6. не выполняет push или merge без явного разрешения человека.

Источник реализации конкретного проекта должен ссылаться на этот стандарт
и дополнительно описывать свои команды, endpoint'ы, конфигурацию и логи.
