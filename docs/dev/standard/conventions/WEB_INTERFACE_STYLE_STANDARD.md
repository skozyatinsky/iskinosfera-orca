> Каноническое правило: **как должен выглядеть и вести себя рабочий

## 1. Где применять

Этот стандарт применяется к рабочим веб-интерфейсам:

- панели менеджера;
- внутренние кабинеты;
- административные разделы;
- очереди заявок и задач;
- формы загрузки файлов;
- таблицы сопоставлений, цен, статусов и ошибок;
- экраны, где человек принимает решение и меняет состояние процесса.

Этот стандарт не является правилом для рекламных страниц, игр, медиа-сайтов,
портфолио и страниц, где главный смысл - выразительная подача, а не
ежедневная работа с данными.

---

## 2. Главный принцип

Интерфейс должен быть похож на рабочее место, а не на рекламную страницу.

Хороший экран отвечает на четыре вопроса:

1. Где я нахожусь?
2. Что требует внимания?
3. Что я могу сделать сейчас?
4. Почему система предлагает именно это решение?

Красота не должна вытеснять плотность, читаемость и скорость принятия
решения.

---

## 3. Базовый стиль

Стиль по умолчанию:

- светлая тема;
- нейтральный фон;
- один основной акцентный цвет;
- мягкие границы и тени;
- плотные, но читаемые таблицы;
- карточки показателей без декоративной перегрузки;
- левое меню;
- верхняя панель с поиском, действиями и профилем;
- понятные статусы;
- боковая панель для объяснений, деталей и истории.

Запрещено:

- делать вид Excel-таблицы вместо веб-интерфейса;
- превращать рабочую панель в рекламную страницу;
- добавлять бессмысленные графики ради красоты;
- смешивать роли и рабочие контуры;
- использовать чужие товарные категории в демо;
- показывать роль пользователя как яркую плашку рядом с ФИО;
- начинать с тёмной темы, если проект не требует её явно.

---

## 4. Темы

Для первого рабочего интерфейса обязательна только светлая тема.

Тёмная тема допустима позже, когда уже стабильны:

- визуальные переменные;
- библиотека компонентов;
- статусы;
- таблицы;
- модальные окна;
- предупреждения и ошибки;
- экспортные документы.

Экспорт в XLSX/PDF/КП всегда делается в светлом деловом стиле и не зависит от
темы интерфейса.

---

## 5. Визуальные переменные

Цвета задаются через переменные, а не разбрасываются по коду.

Базовые значения в стиле BestPrice:

|------------|----------------|----------|
| Фон страницы | `--bg` | `#F3F6FB` |
| Полупрозрачная панель | `--panel` | `rgba(255, 255, 255, 0.92)` |
| Сплошная панель | `--panel-solid` | `#FFFFFF` |
| Основной текст | `--text` | `#102033` |
| Вторичный текст | `--muted` | `#5F6F85` |
| Тихий текст | `--muted-2` | `#94A3B8` |
| Граница | `--line` | `#D9E2EE` |
| Мягкая граница | `--line-soft` | `#EAF0F7` |
| Основной акцент | `--blue` | `#1F5FBF` |
| Фон акцента | `--blue-2` | `#E7F0FF` |
| Успех | `--green` | `#12865A` |
| Фон успеха | `--green-2` | `#E8F7EF` |
| Предупреждение | `--orange` | `#C77803` |
| Фон предупреждения | `--orange-2` | `#FFF3DA` |

остаются теми же.

---

## 6. Типографика

Базовый шрифт: `Inter`, `IBM Plex Sans`, `Manrope` или системный sans-serif.

Размеры:

| Элемент | Размер |
|---------|--------|
| Таблица | 12-13 px |
| Основной текст | 14-16 px |
| Подписи и вторичный текст | 12-13 px |
| Заголовок карточки | 17-20 px |
| Заголовок страницы | 28-34 px |
| Большое число в показателе | 27-34 px |

Правила:

- не уменьшать текст таблиц ниже 12 px;
- не использовать отрицательный межбуквенный интервал;
- не растягивать размер шрифта от ширины окна;
- длинные значения должны переноситься или обрезаться с понятным
  раскрытием, а не ломать сетку.

---

## 7. Компоновка

Базовая рабочая оболочка:

```text
app-shell
├── левое меню     292px
└── main
    ├── верхняя панель  76px
    └── content         рабочая область
```

Норма для широкой версии:

- левое меню закреплено по высоте окна;
- верхняя панель закреплена сверху;
- рабочая область имеет внутренние отступы около `28-30px`;
- таблицы прокручиваются внутри своей области;
- карточки и таблицы не должны менять размер при наведении.

Норма для узкой версии:

- при ширине около `1100px` и ниже сетка перестраивается в одну колонку;
- меню больше не занимает всю высоту;
- формы, карточки и таблицы идут друг за другом;
- пользователь не должен терять главное действие.

---

## 8. Обязательные компоненты

Каждый рабочий интерфейс должен иметь общий набор компонентов:

| Компонент | Назначение |
|-----------|------------|
| Левое меню | основные разделы и текущая зона |
| Верхняя панель | поиск, быстрые действия, профиль |
| Профиль | ФИО, роль серым текстом, круглый аватар |
| Карточка показателя | число, подпись, короткое изменение |
| Таблица данных | строки работы, статусы, действия |
| Статусная метка | состояние строки, заявки или действия |
| Кнопка действия | явная команда пользователя |
| Панель загрузки | загрузка файла или ввод данных |
| Боковая панель | объяснение, альтернативы, история, аудит |
| Модальное окно | подтверждение опасного или важного действия |
| Пустое состояние | что делать, если данных нет |
| Ошибка | что произошло и что можно сделать |
| Загрузка | что сейчас выполняется |
| Нет прав | почему действие недоступно |

Если компонент не нужен на конкретном экране, это нормально. Но если
появляется его задача, используется общий компонент, а не новая разовая
верстка.

---

## 9. Таблицы

Таблица - центральный компонент рабочего интерфейса.

Обязательные свойства:

- читаемый заголовок;
- компактный режим;
- статусные метки;
- действия по строке;
- выделение строки при наведении;
- понятная пустая строка, если данных нет;
- боковая панель или отдельная карточка деталей по клику;
- горизонтальная прокрутка, если колонок много;
- фильтры, если строк больше одной страницы просмотра.

Запрещено:

- делать все данные одним огромным полотном;
- прятать ключевое решение в длинный текст под таблицей;
- смешивать технические поля и пользовательские названия без пояснения;
- показывать `pending` как подтверждённое правило;
- показывать AI/RAG-кандидаты как точные совпадения.

---

## 10. Рабочие панели и аналитика

В интерфейсе продукта показываем то, что помогает действовать:

- очереди;
- спорные строки;
- предупреждения;
- краткие показатели;
- переходы к действиям;
- причины рекомендаций;
- историю решений.

Глубокая аналитика, технический мониторинг, тренды и графики по времени могут
жить в Grafana или другом отдельном контуре. Рабочий интерфейс не должен
становиться заменой BI-системы, если пользователю нужно только принять
операционное решение.

---

## 11. Состояния экрана

У каждого основного экрана должны быть состояния:

- загрузка;
- пусто;
- ошибка;
- нет прав;
- успех;
- частичный результат;
- действие выполняется;
- действие недоступно.

Кнопка, которая запускает долгий процесс, должна менять состояние: текст,
блокировка, индикатор выполнения или понятное сообщение.

---

## 12. Код и реализация

Агент перед изменением интерфейса читает:

1. `docs/ТЕРМИНЫ.md`;
2. этот стандарт;
3. `docs/Дизайн/README.md`;
4. актуальный документ `docs/Дизайн/*__STATUS.md`;
5. существующие CSS-переменные и компоненты проекта.

Правила реализации:

- использовать стек проекта;
- не добавлять тяжёлый frontend-фреймворк без ТЗ;
- не добавлять случайную библиотеку компонентов без причины;
- цвета, радиусы, тени и отступы держать в переменных;
- не писать разовые `style="..."`, если это повторяемый элемент;
- не дублировать компонент ради одного экрана;
- строки интерфейса держать в одном понятном месте, если в проекте есть
  локализация;
- проверять экран на широкой и узкой ширине.

Для FastAPI/Jinja2-проектов допустимый простой стек:

```text
FastAPI + Jinja2 + HTMX при необходимости + CSS-переменные
```

Для React/Next.js-проектов правило то же: сначала существующие компоненты и
переменные проекта, потом новые компоненты.

---

## 13. Документы проекта

Если в проекте есть веб-интерфейс, в `docs/Дизайн/` должны быть:

```text
00_Дизайн_визуальная_система__DONE.md
10_Дизайн_карта_экранов__DONE.md
20_Дизайн_ключевой_сценарий__WIP.md
```

Можно объединить их в один файл, если интерфейс маленький:

```text
00_Дизайн_веб_интерфейс__DONE.md
```

Главное - у агента должен быть один короткий вход, где зафиксированы:

- стиль;
- переменные;
- основные экраны;
- роли;
- состояния;
- что считается готовым.

Валидатор структуры проверяет минимальное правило: если в проекте найдены
признаки веб-интерфейса (`package.json`, `web/`, `frontend/`, `templates/`,
`static/`, `.html`, `.css`, `.tsx`, `.jsx`), то нужны:

- `docs/Дизайн/README.md`;
- хотя бы один Markdown-документ в `docs/Дизайн/`;
- ссылка на `WEB_INTERFACE_STYLE_STANDARD.md` в этом документе.

Для старых живых проектов допустимо переходное исключение: дизайн-документ
проходит проверку без ссылки, если в нём явно зафиксированы утверждённый стиль
и светлая тема. При ближайшей уборке такой документ всё равно лучше дополнить
ссылкой на общий стандарт.

---

## 14. Проверка перед завершением

Перед тем как считать экран готовым, агент проверяет:

- стиль соответствует проектному дизайн-документу;
- нет чужих товарных категорий и случайного демо-текста;
- таблицы читаются;
- статусы различимы;
- главное действие видно без поиска;
- боковая панель не перегружена;
- пустое, ошибочное и загрузочное состояния есть;
- на узкой ширине ничего не перекрывается;
- текст не вылезает из кнопок, карточек и таблиц;
- цвета и размеры не зашиты мимо переменных;
- рабочая панель не стала декоративной.

светлый деловой интерфейс, высокая читаемость, плотные таблицы, понятные
статусы и минимум декоративного шума.
