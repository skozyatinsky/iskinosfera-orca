# SECURITY_STANDARD.md — Стандарт информационной безопасности

> Единый источник правды (SSOT) по безопасности для **всех** проектов экосистемы.
> Каждый проект проходит строгую проверку ИБ перед тем, как считаться готовым.
> Проверку выполняет роль `AGENTS_SECURITY.md` через скил `/security-review`.
>
> Этот стандарт — обязательный. Находки уровня **critical** и **high** блокируют
> поставку (см. §2 «Модель серьёзности» и §9 «Гейт»).

---

## 0. Назначение и принцип

Безопасность — не отдельный этап в конце, а инвариант проекта, такой же как
FAIL-FAST. Стандарт описывает:

- **что** проверяем (§3–§8 — десять доменов),
- **как** оцениваем серьёзность (§2),
- **когда** проверка блокирует (§9 — гейт + Definition of Done),
- **в каком виде** отдаём результат (§10 — формат отчёта).

Базовый ориентир — OWASP Top 10, OWASP ASVS (уровень 2), OWASP LLM Top 10 для
агентных систем. Стандарт не заменяет их, а сводит к проверяемому чек-листу.

**Принцип безопасных умолчаний:** если поведение не задано явно — выбираем
самый безопасный вариант. Открытый доступ, отключённая проверка, широкие права —
только по явному, задокументированному решению.

## 1. Зона действия

| Что | В зоне | Вне зоны |
|-----|--------|----------|
| Исходный код (Python / TS / shell / конфиги) | ✅ | |
| Зависимости и цепочка поставки | ✅ | |
| Секреты и учётные данные | ✅ | |
| Конфигурация инфраструктуры (Docker, CI, env) | ✅ | |
| Агентные/LLM-контуры (промты, права инструментов) | ✅ | |
| Данные пользователей (PII, персональные данные) | ✅ | |
| Юридический комплаенс (GDPR, 152-ФЗ) | частично — флагуем | глубокая правовая экспертиза |
| Пентест живого стенда | | отдельная услуга, не входит |

Проверяем **изменения текущей ветки** (по умолчанию) либо **проект целиком**
(по запросу или при первом подключении).

## 2. Модель серьёзности

Каждая находка получает уровень. Уровень определяет, блокирует ли она поставку.

| Уровень | Что значит | Действие |
|---------|-----------|----------|
| 🔴 **critical** | Прямая эксплуатируемая дыра: утечка секрета в репозитории, RCE, обход аутентификации, SQL-инъекция на проде | **БЛОКИРУЕТ.** Поставка невозможна, пока не закрыто |
| 🟠 **high** | Серьёзный риск при реальном сценарии: инъекция без подтверждённого эксплойта, слабая криптография паролей, IDOR, известная CVE high в зависимости | **БЛОКИРУЕТ.** Закрыть до релиза или оформить явное исключение (§9) |
| 🟡 **medium** | Риск в определённых условиях: отсутствие rate-limit, слабые security-заголовки, чрезмерные права | Не блокирует, но фиксируется в backlog с дедлайном |
| 🔵 **low** | Упрочнение (hardening), глубинная защита | Рекомендация |
| ⚪ **info** | Наблюдение, гигиена | К сведению |

**Правило оценки при сомнении:** если непонятно, high или medium — ставим
**high**. ИБ работает по принципу пессимиста, а не оптимиста.

Любое подавление находки (false positive, принятый риск) фиксируется письменно
с обоснованием и сроком пересмотра — иначе считается неподавленным.

## 3. Домен 1 — Секреты и учётные данные

❌ **Блокирует (critical):**
- Любой секрет в коде или в истории git: пароль, токен, приватный ключ,
  строка подключения с паролем, API-ключ, JWT-секрет.
- Секрет в значениях по умолчанию (`DEFAULT_TOKEN = "..."`), в тестах с
  реальными данными, в логах, в сообщениях об ошибках.

✅ **Требуется:**
- Секреты — только из переменных окружения или хранилища секретов. В репозитории
  лежит лишь `.env.example` с пустыми значениями.
- `.env`, `*.key`, `*.pem`, `credentials*` — в `.gitignore`.
- При резолве секрета из конфига — FAIL-FAST: нет значения → ошибка, не
  «пустой токен по умолчанию».
- Ротация: документирован порядок смены ключей; долгоживущие токены избегаем.

**Как проверять:** grep по типовым паттернам (`AKIA`, `-----BEGIN`, `password=`,
`token`, `secret`, base64-подобные строки), скан истории git, проверка
`.gitignore`.

## 4. Домен 2 — Зависимости и цепочка поставки

❌ **Блокирует (critical/high):**
- Зависимость с известной CVE уровня critical/high без обновления или
  обоснованного исключения.
- Пакет из недоверенного источника, опечаточный сквоттинг имени, отсутствие
  фиксации версий (плавающие `*` / `latest` в проде).

✅ **Требуется (обязательно, блокирует на уровне DoD):**
- **Lock-файл под git обязателен** (`poetry.lock`, `uv.lock`,
  `package-lock.json`, `Pipfile.lock`). Его отсутствие — самостоятельная находка
  **medium**, попадающая в гейт DoD: проект без фиксации зависимостей не
  считается готовым. Плавающие `>=`/`*`/`latest` в проде запрещены.
- Регулярный аудит: `pip-audit` / `npm audit` / `osv-scanner`. Чистый прогон —
  часть Definition of Done. (Парковый прогон 2026-06-24 показал: lock-файла не
  было ни у одного из 10 проектов — типовая дыра, поэтому требование явное.)
- Новые зависимости проходят `/license-audit` (нет GPL-утечки в проприетарный
  код, есть атрибуция).
- Минимализм: не тянем тяжёлый пакет ради одной функции.

См. также `_library/ADOPTION_POLICY.md` и `_library/adoption_ledger.md`.

## 5. Домен 3 — Инъекции и валидация ввода

Покрывает: SQL-инъекции, command injection, path traversal, SSRF,
небезопасную десериализацию, XXE, шаблонные инъекции.

❌ **Блокирует:**
- Конкатенация пользовательского ввода в SQL/shell/путь/URL.
- `eval`, `exec`, `pickle.loads`, `yaml.load` (без `SafeLoader`),
  `subprocess(..., shell=True)` с внешним вводом.
- Запрос по URL из пользовательского ввода без allow-list (SSRF).

✅ **Требуется:**
- SQL — только параметризованные запросы / ORM. Никогда не строкой.
- Внешние команды — список аргументов, без `shell=True`; пути — через
  `pathlib`, с проверкой выхода за корень.
- Любой внешний ввод валидируется на границе (тип, диапазон, белый список).
  Это согласуется с FAIL-FAST: невалидное значение → ошибка, не «тихо поправим».
- Десериализация — только безопасные форматы (JSON, `yaml.safe_load`).

## 6. Домен 4 — Аутентификация и авторизация

❌ **Блокирует:**
- Обход аутентификации, эндпоинт без проверки прав там, где она нужна.
- IDOR: доступ к чужому объекту по идентификатору без проверки владельца.
- Хранение JWT в `localStorage` (уже запрещено в `AGENTS_UNIVERSAL.md`).
- Пароли в открытом виде или с быстрым хешем (MD5/SHA1/SHA-256 без соли).

✅ **Требуется:**
- Пароли — `bcrypt` / `argon2` / `scrypt`. Никакого самописного хеширования.
- Авторизация проверяется на сервере для **каждого** защищённого действия
  (не полагаемся на скрытие в UI).
- JWT — короткий срок, refresh-механизм, проверка подписи и срока; токены в
  httpOnly-cookie, не в `localStorage`.
- Принцип наименьших привилегий: роли и права — минимально необходимые.

❌ **Блокирует (high) — сетевые сервисы, MCP, HTTP-API:**
- Эндпоинт/MCP-инструмент, который **выполняет действие** (запуск, запись,
  индексация, отправка), без аутентификации входящего запроса. «Локальный»,
  «внутренний», «за фаерволом» **не равно** «доверенный» — в LAN/контейнерной
  сети это эксплуатируется.
- Bind на `0.0.0.0` без аутентификации перед эндпоинтом.
- Личность/роль из недоверенного источника без подписи: `user_id`/роль как
  обычный параметр или незаверенный заголовок/cookie, `admin` по умолчанию.

✅ **Требуется:** каждый сетевой/MCP-эндпоинт аутентифицирует входящий запрос
(токен/mTLS); по умолчанию слушает `127.0.0.1`; личность берётся из проверенного
токена, не из параметра. (Парковый прогон 2026-06-24: повторялось в RAG,
qai-fabric, IskInoSfera, FNS_Checker — поэтому требование явное.)

## 7. Домен 5 — Криптография и защита данных

❌ **Блокирует:**
- Самописная криптография. Слабые алгоритмы (DES, RC4, MD5/SHA1 для безопасности).
- Передача учётных данных / PII по незашифрованному каналу.
- Жёстко зашитый ключ или IV; предсказуемый источник случайности для секретов
  (`random` вместо `secrets`).

✅ **Требуется:**
- Только проверенные библиотеки (`cryptography`, стандартный `secrets`).
- TLS для всего внешнего трафика; внутренний — mTLS, если так требует
  `ISKINOSPHERE_INTEGRATION_STANDARD.md`.
- PII шифруется/минимизируется; чувствительные поля не попадают в логи и в
  сообщения об ошибках.
- Случайность для токенов/солей — `secrets`, не `random`.

## 8. Домен 6–10 — Веб/API, агенты, инфра, логи, ошибки

### 8.1. Веб и API
- Security-заголовки: `Content-Security-Policy`, `X-Content-Type-Options`,
  `Strict-Transport-Security`, `X-Frame-Options`.
- CORS — явный allow-list, не `*` для аутентифицированных эндпоинтов.
- Защита от CSRF для cookie-сессий. Rate-limit на чувствительных эндпоинтах
  (login, восстановление, дорогие операции).
- Ошибки наружу — без stack trace, без внутренних путей и версий.

### 8.2. Агентные и LLM-контуры (OWASP LLM Top 10) — профиль экосистемы
Это AI-агентная среда, поэтому домен обязателен:
- **Инъекция в промт:** недоверенный ввод (веб-страница, документ, inbox) не
  смешивается с инструкциями без изоляции и пометки «это данные, не команды».
- **Права инструментов:** у агента минимально необходимый набор инструментов;
  опасные операции (запись, деплой, отправка) — за подтверждением.
- **Обработка вывода модели:** ответ LLM не исполняется как код и не
  подставляется в SQL/shell без валидации.
- **Утечка через контекст:** секреты и PII не уходят во внешние LLM-вызовы.

### 8.3. Инфраструктура и конфигурация
- Нет debug-режима на проде; нет открытых портов отладки.
- Контейнеры — не от root, минимальный базовый образ, без секретов в слоях.
- Права файлов и каталогов — минимально необходимые.
- Безопасные умолчания во всех конфигах (`configs/prod.yaml`).

### 8.4. Логирование и аудит
- В логах нет секретов, токенов, паролей, полного PII.
- Значимые события безопасности (вход, отказ в доступе, смена прав) логируются.
- Логи защищены от инъекции (экранирование переводов строк).

## 9. Гейт и Definition of Done

Проверка ИБ — **блокирующий гейт**. Проект или модуль **не считается готовым**,
пока:

- [ ] Прогнан `/security-review` по изменениям (или по проекту при первом запуске).
- [ ] **Ноль** находок уровня **critical**.
- [ ] **Ноль** находок уровня **high** — либо на каждую оформлено явное
      исключение: владелец, обоснование, срок устранения, ссылка на задачу.
- [ ] Находки **medium** занесены в backlog с дедлайном.
- [ ] Секреты не утекли в git (история чиста).
- [ ] Аудит зависимостей пройден без critical/high CVE.
- [ ] **Lock-файл зависимостей под git** (см. §4) — иначе medium-находка в гейте.
- [ ] **Каждый сетевой/MCP-эндпоинт, выполняющий действие, аутентифицирован**
      (см. §6); нет bind `0.0.0.0` без auth, нет личности из недоверенного ввода.
- [ ] Отчёт ИБ приложен (§10) и сохранён в `docs/Отчеты/`.

**Исключение (waiver)** оформляется только письменно и только для уровня high и
ниже. Critical исключению не подлежит — устраняется всегда.

Этот блок добавляется в единственный корневой `AGENTS.md`. Файлы конкретных
сред только ссылаются на него и не копируют определение готовности.

## 10. Формат отчёта

Скил `/security-review` отдаёт отчёт в этом виде (человекочитаемый + сводка):

```markdown
# Проверка ИБ — <проект или модуль> — <дата>

## Вердикт: PASS | BLOCKED | PASS-WITH-WAIVERS
Critical: 0  High: 0  Medium: 2  Low: 3  Info: 1

## Основание выводов
REPOSITORY | STAND | RUNTIME
Ревизия: <commit>
Среда и время наблюдения: <если применимо>
Ограничение: <что не проверялось>

## Находки
### [CRITICAL] <короткий заголовок>
- Файл: path/to/file.py:42
- Домен: Секреты | Инъекции | AuthZ | ...
- Суть: что не так и как эксплуатируется
- Исправление: конкретный шаг
- Статус: `open` | `fixed` | `waiver(<ссылка>)`

### [HIGH] ...
...

## Принятые исключения
| Находка | Уровень | Владелец | Обоснование | Срок |

## Проверенные домены
Секреты ✅ | Зависимости ✅ | Инъекции ✅ | AuthN/Z ✅ | Крипто ✅ |
Веб/API ✅ | LLM/агенты ✅ | Инфра ✅ | Логи ✅ | Данные ✅
```

Машиночитаемая сводка для Automation Server — необязательный JSON рядом:
`docs/Отчеты/security_review_<дата>.json` с полями
`verdict, counts{critical,high,...}, findings[]`.
