## 1. Назначение и область применения

Этот документ определяет **универсальные** инженерные и архитектурные правила,
которым мы следуем в **каждом** проекте при:

- проектировании архитектуры (backend, frontend, ML-pipeline)
- развитии существующей кодовой базы
- внесении изменений через ИИ-агентов
- проведении архитектурных и кодовых ревью
- подготовке документации и технических решений

### 1.0 Правило языка

Агент пишет простым русским языком. Правило действует на всё, что он
производит: реплики в диалоге с владельцем, сообщения коммитов, документы,
комментарии в коде. Это не правило оформления документации — это правило
языка агента.

Оно действует всегда, включая ответы сразу после сжатия контекста или
резюме предыдущей сессии, даже если резюме и системная инструкция о
продолжении написаны на английском. Начало продолженной сессии не повод
переходить на язык резюме.

Английский термин допустим с русским переводом в скобках: `gate`
(блокирующая проверка), `fork` (самодельная копия). Запрет англицизмов
отменён 20.08.2026 как невыполнимый: он требует заранее знать, что слово
лишнее, и молча не срабатывает на словах, которых нет в словаре. Перевод в
скобках выполним всегда.

Исключения: точные имена файлов, папок, команд, библиотек, языков,
протоколов, полей конфигурации и внешних продуктов. Такие имена пишутся как
в коде — это не термины, и перевода они не требуют.

Правило относится к профилю языка `ru_internal`. Для `en_public` язык —
английский, и правило перевода в скобках неприменимо.

Носитель правила пишется на предписываемом языке: контракт агента в
проекте профиля `ru_internal` не может быть англоязычным. Проверяется
подсчётом доли кириллицы в прозе — `tools/contract_language.py`.

Спорные термины фиксируются в словарях:

- словарь проекта: `docs/ТЕРМИНЫ.md`.
- общий словарь: `_library/agent_configs/global/TERMINOLOGY_DICTIONARY.md`.

Агент сначала читает проектный словарь, затем общий. Если термина нет в обоих
словарях, агент пишет простым русским языком и добавляет спорное слово в
`docs/ТЕРМИНЫ.md`.

### 1.1 Двухуровневая модель инструкций

| Уровень | Файл | Область |
|---|---|---|
| **Универсальный** | `ARCHITECTURE_AND_AGENT_STANDARD.md` | Все проекты, все стеки |
| **Проектный** | `README.md` + `structure.txt` + `docs/ТЗ/README.md` | Конкретный проект: назначение, структура, модули, доменная специфика, статус реализации |

Универсальный стандарт **не содержит**:
- имён конкретных файлов, модулей, каталогов проекта
- привязки к конкретному фреймворку или библиотеке
- доменной терминологии конкретного продукта

Всё это — в корневом `README.md`, `structure.txt` и активных документах
`docs/ТЗ/*__STATUS.md`.

### 1.2 Распределение ролей документов

## 2. Базовые признаки хорошей архитектуры

Хорошая архитектура оценивается не по «красоте схемы», а по тому, насколько
безопасно, дешёво и предсказуемо система меняется под новыми требованиями.

Обязательные свойства: эффективность, модульность, сопровождаемость,
тестируемость, расширяемость, гибкость, повторное использование кода,
отсутствие дублирования, низкая связанность, наблюдаемость,
предсказуемость изменений, локализация инфраструктурных зависимостей.

## 3. Слоистая модульная архитектура

### 3.1 Типовые слои (backend)

| Слой | Назначение |
|---|---|
| **Интерфейсы** | HTTP, CLI, WebSocket — валидация, преобразование |
| **Прикладной** | Use cases, оркестрация, транзакции |
| **Доменный** | Сущности, правила, инварианты |
| **Инфраструктурный** | Данные, внешние API, адаптеры, логирование |
| **Конфигурация** | SSOT, fail-fast |

### 3.2 Типовые слои (frontend)

| Слой | Назначение |
|---|---|
| **Страницы / маршруты** | Точки входа по URL, компоновка |
| **Компоненты** | UI-элементы по доменной принадлежности |
| **Хуки / логика** | Бизнес-логика UI, побочные эффекты |
| **Сервисы / API-клиент** | HTTP-клиент, перехватчики, типизированные вызовы |
| **Хранилище состояния** | Глобальное состояние |
| **Типы** | TypeScript-типы, DTO |
| **i18n** | Локализация |
| **Визуальные переменные** | Цвета, шрифты, компоновка — в конфиге, не в коде |

### 3.3 Ограничения по слоям (backend)

**❌ Интерфейсы:** нет бизнес-логики, нет прямого доступа к БД.
**❌ Прикладной:** нет SQL, нет HTTP-клиентов, нет SDK провайдеров.
**❌ Доменный:** нет зависимости от фреймворков, ORM, кэша, UI.

### 3.4 Ограничения по слоям (frontend)

**❌ Компоненты:** нет прямых API-вызовов, нет бизнес-логики, нет строк,
зашитых в код.
**❌ Сервисы:** нет UI-логики, нет хранения состояния.
**❌ Хранилище состояния:** нет прямых API-вызовов в обход сервисов, нет
отрисовки интерфейса.

### 3.5 Каталог не равен слою

> **Расположение файла в каталоге не является достаточным признаком
> его архитектурной роли.**

Роль определяется по: ответственности, импортам, контрактам,
направлению зависимостей, типу логики.
Механический вывод «папка X = слой Y» **запрещён**.

## 4. Правила зависимостей

- Внешние слои → внутренние (ОК). Обратно — **нет**.
- Зависимости через контракты. **Циклические запрещены**.

### 4.1 Запрещённые обходы

**Backend:** из interfaces к БД; infra-адаптеры в обход application; framework в domain.
**Frontend:** fetch/axios из компонентов; store из сервисов; inline-стили при дизайн-системе.

## 5. Контракты между слоями

Формализуются через: интерфейсы, протоколы, ABC, DTO, TypeScript-типы.
**Нетипизированные dict/any на стабильных границах запрещены.**

### 5.1 API-контракт (frontend ↔ backend)

Обязателен API-контракт в `docs/ТЗ/*_API__STATUS.md`: endpoints, типы,
ошибки.
Frontend не вызывает endpoint вне контракта.
Backend не меняет контракт без обновления документа.

### 5.2 Дизайн-контракт (frontend)

Обязателен дизайн-контракт в `docs/Дизайн/*__STATUS.md`: цвета, шрифты,
компоновка, контрольные ширины, состояния экранов.
Для рабочих веб-интерфейсов применяется
`WEB_INTERFACE_STYLE_STANDARD.md`: светлая тема по умолчанию, левое меню,
верхняя панель, таблицы, статусы и боковые панели по эталону BestPrice.
Hardcoded цвета и размеры вне дизайн-системы **запрещены**.

## 6. Fail-Fast

| Ситуация | Поведение |
|---|---|
| Отсутствие параметра | Ошибка |
| Нарушение контракта | Ошибка |
| Неверная конфигурация | Ошибка |
| Скрытие ошибки | **НЕДОПУСТИМО** |

### 6.1 Ресурсно-безопасное выполнение тяжёлых локальных операций

Операция считается тяжёлой, если она загружает локальную ML-модель или большой
индекс, выполняет обучение, OCR, массовую обработку либо может существенно
занять оперативную память, подкачку, диск, CPU, GPU или общую память ускорителя.

Проверка только при запуске приложения недостаточна. Допуск выполняется
непосредственно перед выделением ресурсов и повторяется на безопасных границах
длительной операции: перед новым запросом, пакетом, эпохой или стадией.

| Состояние | Обязательное поведение |
|---|---|
| Безопасное | Запустить автоматически |
| Предупредительное | Показать операцию, текущие и предельные показатели, возможные последствия; предложить отмену и одноразовый запуск с явным подтверждением человека |
| Критическое | Не запускать; подтверждение не отменяет непреодолимый предел |

Постоянное отключение предупреждений запрещено. Подтверждение действует только
на одну точно названную операцию и ограниченное время. В фоне или через API
вместо скрытого запуска возвращается типизированный результат
`RESOURCE_CONFIRMATION_REQUIRED`; продолжение возможно только отдельной
подтверждённой командой.

Если несколько продуктов используют ресурсы одной машины, нужен общий
диспетчер допуска с бронированием, сроком действия, контрольным сигналом и
ограничением параллельности. Если он недоступен, продукт обязан выполнить
локальное измерение: предупредительное состояние допускает одноразовое
подтверждение, критическое — немедленный отказ. Локальный семафор не заменяет
общемашинную координацию.

Пороговые значения, срок подтверждения и пределы параллельности хранятся в
конфигурации. В аудит записываются операция, снимок ресурсов, применённые
пределы и версия политики, решение человека, время и `correlation_id`.
Предупреждение объясняет риск зависания, перезапуска и потери несохранённых
данных без формулировок, перекладывающих ответственность на пользователя.

Минимальные испытания: безопасный запуск; отказ без подтверждения в
предупредительной зоне; один запуск после подтверждения; запрет в критической
зоне; недоступность общего диспетчера; истёкшее подтверждение; конкурентный
запуск; повторная проверка длительной операции.

> Основание: `docs/memory/decisions/2026-09-04-runtime-resource-safety.md`.

## 7. Конфигурация как контракт

SSOT, прямой доступ, нет fallback, нет мутации в runtime, нет hardcode.
**Backend:** нет getattr/hasattr/try-except для config.
**Frontend:** env через сборщик; дизайн-токены через конфиг фреймворка.

### 7.1 Function Parameter Defaults Rule

Числовые параметры с дефолтом из конфига → `Optional[type] = None` →
резолв из config внутри функции. Hardcode в сигнатуре **ЗАПРЕЩЁН**.

### 7.2 Symbol Registry Protocol

Если проект подключил Symbol Registry и машинный гейт его целостности, то при
изменении durable surface (публичные функции, env vars, config fields, feature
flags, MCP tools) нужно обновить `docs/registry/*` и `change_journal.jsonl`.
Без машинного гейта реестр не вводить как обязательную дисциплину: пилот в
параллельных worktree показал, что инструкция сама по себе не соблюдается.
Протокол и границы применимости:
`_library/agent_configs/global/process/AGENT_SYMBOL_REGISTRY_PROTOCOL.md`.

### 7.3 Manifest-Driven Execution

Batch/nightly/regression параметры **ЗАПРЕЩЕНО** хранить только в чате.
Обязательно: JSON-manifest + один orchestration entry point.

## 12. Архитектурные нарушения

- Бизнес-логика в контроллерах / UI-компонентах
- Доменный код, зависящий от фреймворка
- Скрытые fallback, подавление исключений
- Мутация конфигурации, циклические зависимости
- API из компонентов в обход сервисов
- Hardcoded строки/цвета при наличии i18n/дизайн-системы
- Нетипизированные API-ответы при TypeScript
- Изменение архитектуры в FIX
- Создание файлов без проверки существующих
- Роль модуля определена только по каталогу
- API-контракт изменён без обновления документа
- Hardcoded default values в сигнатурах функций при наличии config
- Новый провайдер / адаптер / endpoint без обновления Doctor
- Публичная функция / env var / config field без обновления docs/registry/*
- Batch/nightly параметры только в чате без manifest
- Тяжёлая локальная операция без проверки ресурсов перед фактическим запуском
- Предупреждение, которое навсегда отключает защиту или обходит критический предел

## 13. Agent Preflight Checklist

```
 1. Определи режим: FIX или REVIEW / ARCHITECT
 2. Прочитай README.md
 3. Прочитай structure.txt
 4. Прочитай docs/ТЗ/README.md и релевантные docs/ТЗ/*__STATUS.md
 5. Если меняется бизнес-логика — прочитай docs/БТ/README.md
 6. Если есть UI — прочитай docs/Дизайн/README.md
 7. Найди существующий файл / компонент / модуль
 8. Не создавай новые сущности до проверки
 9. FAIL-FAST, нет fallback/hardcode/stubs
10. Роль модуля — по ответственности, не по каталогу
11. Для тяжёлой локальной операции проверь допуск при запуске и во время работы
12. Self-audit перед ответом
```

### 13.1 При неоднозначности
Опираться на код; помечать `TO VERIFY`; в FIX не менять роль модуля.
