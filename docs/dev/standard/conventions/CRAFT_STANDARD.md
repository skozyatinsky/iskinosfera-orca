# Craft Standard — стандарт мастерства письма и интерфейсов

> Каноническое правило: **как написан текст и как устроен интерфейс** в любом
> проекте, который собирает Архитектор.
>
> Это слой **«как пишем»**. Слой **«где лежит»** — в `DOCUMENTATION_STANDARD.md`,
> слой **«как называется»** — в `FILE_AND_FOLDER_STANDARD.md`. Они не
> пересекаются: можно идеально разложить папки и при этом писать плохо.
>
> Читается ДО написания README, ТЗ, обзорных документов и публичного API.
> Противоречия решаются в пользу этого стандарта, если проект не заявил явное
> исключение в своём `CLAUDE.md` / `AGENTS.md`.

---

## 0. Откуда взято

Стандарт собран не по «самым звёздным» репозиториям, а по практике авторов,
чьё ремесло держит проверку временем: Карпаты (`nanoGPT`, `micrograd`),
Рамирес (FastAPI), Ронахер (Flask), Рейтц (`requests`), Шолле (Keras),
ван Россум (Zen of Python), Марш (`ruff`, `uv`), sindresorhus (1000+ модулей
одного скелета), donnemartin (`system-design-primer`).

**Звёзды — сигнал охвата, а не мастерства.** Списки и учебные карты
(`awesome`, `developer-roadmap`, `coding-interview-university`) набирают
сотни тысяч звёзд за счёт огромной аудитории учащихся — это контент-продукты,
а не инженерные артефакты. Их структуру **не копируем** (см. §10).

---

## 1. TL;DR — девять законов

Читателю с одной минутой хватит этой таблицы. Подробности и примеры — ниже.

| № | Закон | Одной строкой | Чей урок |
|---|-------|---------------|----------|
| 1 | Интерфейс раньше реализации | Сначала пиши, *как этим пользуются в 5 строк* | Рейтц, Рамирес, Ронахер |
| 2 | Минимум как дисциплина | Выкинь всё, что не несёт смысла | Карпаты, Суцкевер, Рейтц |
| 3 | Прогрессивное раскрытие | Простое — просто, сложное — ниже | Шолле, Рамирес |
| 4 | Один очевидный способ | На каждый выбор — рекомендованный вариант по умолчанию | ван Россум, Марш |
| 5 | Рассуждение, а не анонс | Тезис → почему → неопределённость | Амодеи |
| 6 | Показывай результат | Пример без вывода — неполный | Рамирес, МакГьюган |
| 7 | Один скелет на всё | Читатель не переучивается между репо | sindresorhus, lucidrains |
| 8 | Слоистая глубина | Один документ под разные бюджеты чтения | donnemartin |
| 9 | Стиль под документ | Эссе для решений, минимум для справки | свод всех выше |

## 2. Закон 1 — интерфейс раньше реализации

Сначала пишется блок «использование за 5 строк», и эти 5 строк **реально
исполнимы**. Только потом — реализация. Если интерфейс нельзя описать в пять
строк, проблема в интерфейсе, а не в описании.

**До** (интерфейс прячется за обзором архитектуры):

```markdown
## Архитектура
Модуль состоит из слоёв ingest, normalize, index, retrieve, rank.
Точкой входа служит фасад RetrievalService, инициализируемый фабрикой...
```

**После** (RAG, реальный README):

```markdown
## Проверка

    python -m pytest tests/ -x -q
    python start_server.py
```

Читатель за 5 секунд знает, как запустить и проверить. Архитектура — ниже,
для того, кто дочитал.

**Проверка:** в первых 15 строках README/раздела есть исполнимый путь
«как этим пользуются».

---

## 3. Закон 2 — минимум как дисциплина

`nanoGPT` Карпаты — это два файла, и в них ничего нельзя выкинуть без потери
смысла. Это цель: не «коротко ради красоты», а «осталось только несущее».

**Тест nanoGPT:** выбрось половину документа. Потерялась суть? Если нет —
половина была лишней.

Типичные кандидаты на удаление: вступления «в этом документе мы рассмотрим»,
повтор того, что уже сказано в заголовке, перечисление всех опций там, где
нужен один вариант по умолчанию, абзацы-связки без фактов.

**Проверка:** каждый абзац отвечает на вопрос «что отсюда узнаёт читатель?».
Если ответа нет — абзац удаляется.

---

## 4. Закон 3 — прогрессивное раскрытие

Keras Шолле: «простые вещи — просто, сложные — возможно». Первый пример
тривиален; крайние случаи, настройки и оговорки идут ниже по документу, а не
в начале.

Порядок внутри документа: **частый случай → редкий случай → крайний случай**.
Не наоборот.

**Проверка:** первый пример раздела — самый короткий рабочий путь, без
необязательных параметров.

---

## 5. Закон 4 — один очевидный способ

Дзен Python: «должен быть один — желательно единственный — очевидный способ».
Марш доказал это инструментами: `ruff` и `uv` заменили зоопарк одним
быстрым выбором с разумными умолчаниями.

На каждый выбор в документе **назван рекомендованный вариант**. «Можно так,
можно эдак» без рекомендации — это переложенное на читателя решение.

**До:** «Запускать можно через `python start.py`, или `make run`, или из IDE».
**После:** «Запуск: `python start.py`. (Альтернативы — в §Эксплуатация.)»

**Проверка:** ни один выбор не оставлен читателю без варианта по умолчанию.

---

## 6. Закон 5 — рассуждение, а не анонс

Эссе Амодеи держат **тезис → почему → явно названную неопределённость**, а не
список фич. Это формат для *решающих* документов: обзор БТ, ADR, обзор ТЗ.

Решение без названной альтернативы и без названного риска — это анонс, а не
рассуждение. Читатель не может его оспорить, значит не может ему доверять.

**Проверка:** ключевой документ начинается с тезиса и допущений; у каждого
важного решения названы отвергнутая альтернатива и принятый риск.

---

## 7. Закон 6 — показывай результат

У Рамиреса каждый пример FastAPI показывает свой ответ; у МакГьюгана в README
`rich` — скриншоты вывода. Пример без показанного результата заставляет
читателя выполнять его в голове.

**Проверка:** у каждого примера кода/команды показан его вывод, либо явно
сказано, что вывода нет.

---

## 8. Закон 7 — один скелет на всё

sindresorhus держит больше тысячи модулей по одному скелету (Install / Usage /
API), и читатель ни разу не переучивается. lucidrains — то же на 200+
репозиториях ИИ-архитектур. **Это и есть механизм единообразия по всем
проектам экосистемы.**

Единый скелет README проекта:

```markdown
# <Имя>

<Одна фраза: что это и для кого.>

## Быстрый вход
<Точки входа: главные файлы и зоны кода.>

## Проверка
<Исполнимые команды: тесты + запуск.>

## Документация
<Ссылка на docs/README.md и docs/ТЕРМИНЫ.md.>
```

**Проверка:** README проекта совпадает по скелету с остальными проектами
экосистемы; читатель, пришедший из соседнего проекта, не переучивается.

## 9. Закон 8 — слоистая глубина

`system-design-primer` donnemartin обслуживает и того, у кого 5 минут, и того,
у кого 2 часа: TL;DR → краткий обзор → глубокое погружение. Один документ,
читатель сам выбирает бюджет.

Крупные документы (от ~300 строк) строятся слоями:

1. **TL;DR** — таблица или абзац, дающий суть за минуту (как §1 этого файла).
2. **Обзор** — основной текст для того, кто принимает решение.
3. **Глубина** — детали, оговорки, крайние случаи для исполнителя.

**Проверка:** документ длиннее ~300 строк имеет TL;DR в начале.

---

## 10. Закон 9 — стиль под документ (и анти-паттерны)

Заимствование лучших — это выбор *какого* стиля под *какой* документ, а не
один тон на всё. Смешивать нельзя:

| Тип документа | Стиль | Закон-ориентир |
|---------------|-------|----------------|
| Обзор БТ, ADR, обзор ТЗ | рассуждение (эссе) | 5, 8 |
| README, инструкция запуска | минимум, справка | 1, 2, 6 |
| Справочник API, реестр | один скелет, показ результата | 6, 7 |
| Дизайн-документ | прогрессивное раскрытие | 3 |

**Анти-паттерны** (прямой запрет):

1. **Звёзды ≠ мастерство.** Не оформляй проект как `awesome`-список или
   roadmap-картинку. Высокий охват чужого контента не равен качеству твоего
   артефакта.
2. **Эссе в справке.** Инструкция запуска в стиле длинного рассуждения — это
   та самая массовая многословность, от которой уходим.
3. **Минимум в решении.** ADR из трёх строк без альтернатив и рисков —
   нечего оспорить, нечему доверять.

## 11. Первый экран README

Частный, но решающий случай закона 1. За **20 секунд** читатель первого экрана
должен ответить: что это, для кого, какую боль закрывает, какой результат
даёт, можно ли быстро попробовать, куда идти дальше.

**Запрещённые начала** (пустой шум вместо ценности):

```text
Данный проект предназначен...
This repository contains...
Проект реализует...
Набор скриптов для...
Система, использующая современные технологии...
```

**Формула открытия** — две сильные фразы:

```text
<Проект> превращает <проблемный вход> в <полезный результат>
с помощью <ключевой механизм>.

Он нужен <аудитория>, которым важно <выгода> без <типичная боль/риск>.
```

**До:**

```text
# Document Processor
Данный проект предназначен для обработки документов с использованием
современных методов искусственного интеллекта.
```

**После:**

```text
# Document Processor
Document Processor превращает PDF, DOCX и HTML в нормализованные фрагменты
для локального RAG с повторяемой индексацией и трассировкой источников.
Он нужен командам, которым нужен приватный поиск по внутренним документам
без отправки данных во внешние сервисы.
```

**Проверка:** после первого экрана читатель отвечает на все шесть вопросов
выше; начало не входит в список запрещённых.

## 12. Честные ограничения

Раздел ограничений — обязательный, а не признак слабости. Он снижает риск
неправильного использования и экономит время следующего читателя.

Документ (или раздел) ограничений честно перечисляет: что не поддерживается,
технический долг, нестабильные места, риски, и то, что требует подтверждения
владельцем. Неподтверждённое помечается `TODO`, `NEEDS_CONFIRMATION`,
`UNKNOWN` — а не выдаётся за факт.

**Проверка:** у проекта есть актуальный раздел ограничений; в документах нет
выдуманных возможностей.

## 13. Чек-лист ревью

Перед принятием изменений в документ или публичный интерфейс:

- [ ] В первых ~15 строках есть исполнимый путь «как пользуются» (з.1).
- [ ] Пройден тест nanoGPT: лишнего нет (з.2).
- [ ] Первый пример — самый короткий рабочий путь (з.3).
- [ ] У каждого выбора назван вариант по умолчанию (з.4).
- [ ] У решающего документа есть тезис, альтернатива, риск (з.5).
- [ ] У каждого примера показан его вывод (з.6).
- [ ] README совпадает по скелету с другими проектами (з.7).
- [ ] Документ >300 строк имеет TL;DR (з.8).
- [ ] Стиль соответствует типу документа; анти-паттерны §10 не нарушены (з.9).
- [ ] Первый экран README проходит 20-секундный тест (§11).
- [ ] У проекта есть актуальный раздел ограничений; нет выдуманных возможностей (§12).

Чек-лист встроен в `/review-architecture` и `/finish-module`. Стандарт держится
только тем, что его проверяют на каждом ревью.

## 14. Что заимствовать у авторов (и что не копировать)

Образец выбирается не по числу звёзд, а по переносимому инженерному паттерну.
Брать суть, отклонять форму:

| Источник | Что брать | Что не копировать |
|---|---|---|
| sindresorhus | единый скелет README на сотнях пакетов; одна задача на пакет | `awesome`-список как структуру инженерного проекта |
| Карпаты | минимализм, воспроизводимость, честные ограничения, один путь запуска | отсутствие справочника там, где проект уже production |
| Рамирес (FastAPI) | tutorial → концепции → справочник; examples-first | избыточную разветвлённость для маленького проекта |
| Ронахер (Flask) | quickstart, паттерны, точки расширения, аккуратный справочник API | исторические особенности старых проектов |
| Рейтц (requests) | человеческий первый экран, простые примеры до глубины | маркетинговую стилизацию без точной справки |
| Марш (uv/ruff) | guides / concepts / reference, строгая навигация | тяжёлый doc-site для малого проекта |
| Шолле (Keras) | короткие воспроизводимые примеры | notebook-only подход для production |
| donnemartin | слоистую глубину: TL;DR → обзор → погружение | interview-prep формат как структуру проекта |

Итог одной строкой: **брать дисциплину инженерного мышления, а не популярность
формы.** См. анти-паттерн §10.1 «звёзды ≠ мастерство».

## 15. Распространение по проектам

Стандарт — глобальный. В проект он попадает через `.claude/imports.yaml`:

```yaml
  - id: standard.craft
    source_path: agent_configs/global/CRAFT_STANDARD.md
    local_path: docs/dev/standards/CRAFT_STANDARD.md
    mode: reference
```

Обновление — через `/sync-standards`, как у остальных глобальных стандартов.
Один файл — один источник правды для всех 5 проектов.
