# Adoption Policy — Регламент заимствований и апстрим-синка

> Правила работы с внешним кодом, идеями и артефактами, которые мы затащили к себе.
> Единственный источник истины о том, **что мы у кого взяли** — `_library/adoption_ledger.md`.
> Этот файл описывает **как** его вести.

---

## Принципы

1. **Любое заимствование фиксируется в ledger.** Нет записи → считается, что код наш. Это опасно: потеряем контекст, не увидим обновлений, можем нарушить лицензию.
2. **Форк = ответственность.** Взяли — значит отвечаем за синхронизацию (если `watch: true`) или за заморозку (если `watch: false`).
3. **Ledger — не архив, а инструмент.** Читается Scout-модулем и скилами `/update-library`, `/analyze-and-adopt`.
4. **Источник пишется один раз, состояние обновляется.** При апстрим-синке правим `source_commit` и `last_checked`, не создаём новую строку.

---

## Стратегия заимствования (adoption_type)

При любом заимствовании сразу выбери **одну** из трёх стратегий. Это определяет всё дальнейшее поведение (watch, обработка апдейтов, лицензия, атрибуция).

| `adoption_type` | Что это | Примеры | Как обрабатывается апдейт апстрима |
|---|---|---|---|
| **fork** | Код/артефакт скопирован и живёт у нас как копия. Мы — производные от апстрима | Скопировали SKILL.md из anthropic/skills и адаптировали | **Diff применяется** к нашей копии (merge / cherry-pick / ручной патч) |
| **reimplement** | Мы написали своё по мотивам или по спеке. Апстрим — источник идей, не источник кода | Подсмотрели алгоритм в MIT-проекте и написали свою реализацию; clean-room от GPL-проекта; архитектурный паттерн из блога, применённый в стандарте | **Diff не применяется автоматически**. Читаем изменения апстрима как материал для решения: переписать ли **наше**. Подтипы через `scope`: `discrete` (у нас отдельный артефакт) / `diffuse` (идея разлита по коду, нет одного файла) |
| **dependency** | Используется как внешний пакет через package manager. Код физически не у нас | `npm i @modelcontextprotocol/server-postgres`, `pip install playwright` | Апдейт = поднять версию в манифесте. Diff не смотрим, читаем релиз-нотес |

### Как выбрать

```
Код физически лежит в нашем репо? ─── нет ──▶ dependency
  │
  да
  │
  ▼
Наш код — прямая копия апстрима (с правками или без)? ─── да ──▶ fork
  │
  нет (написали сами по мотивам/спеке)
  │
  ▼
                                                           reimplement
```

### fork vs dependency — ключевая разница

| | fork | dependency |
|---|---|---|
| Где код | У нас в репо | У апстрима, в package registry |
| Чем управляем | Кодом | Только версией в манифесте |
| Апдейт | Merge diff или отказ | Сменить строчку в manifest |
| Кто чинит баг | Мы | Апстрим (или мы через PR туда) |

### reimplement с `scope: diffuse`

Частный случай: идея растворена в нашем коде, нет одного файла-эквивалента. Например, «адаптер+миксин» из статьи применён в `ARCHITECTURE_AND_AGENT_STANDARD.md`. Обрабатывается так же, как любой reimplement — апстрим-diff как материал для пересмотра, не для применения.

### Поле `modifications` (опционально)

Имеет смысл только при `fork`:
- `verbatim` — копия 1:1
- `adapted` — существенно правили

При `reimplement` и `dependency` — `n/a`.

## Когда добавлять запись

| Сценарий | Обязательно? |
|---|---|
| Скопировали SKILL.md из внешнего репо | **Да** |
| Адаптировали код (MIT/Apache) — переписали по мотивам | **Да** |
| Clean-room (по спеке, не глядя в код) | **Да** — фиксируем источник идеи |
| Взяли MCP-сервер как зависимость (npm i, pip install) | **Да**, с пометкой `kind: dependency` |
| Подсмотрели паттерн в блоге/доке, реализовали сами | **Да**, с пометкой `kind: pattern` |
| Прочитали doc, ничего не взяли | Нет |

## Уровень отслеживания (watch flag)

| `watch: true` | `watch: false` (frozen) |
|---|---|
| Scout при `/scan_watch` проверяет апстрим-обновления | Scout игнорирует |
| Обновление апстрима → `inbox/` со `status: update_available` | — |
| Требует активного сопровождения | Одноразовый форк, дальше живёт сам |

**По умолчанию:** `watch: true` для A-источников, `watch: false` для C.

Для **dependency** watch значит «следить за релизами», не за коммитами.

## Отказ от конкретного обновления

Решение «не брать этот апдейт» — **такое же событие**, как приём. Фиксируется в записи ledger, иначе через полгода непонятно, почему отстали.

Три уровня отказа:

| Уровень | Поле в записи | Смысл |
|---|---|---|
| **Разовый отказ** | `declined_commits: [sha1, sha2]` + `decline_reasons: {sha1: "...", sha2: "..."}` | Именно эти коммиты мы посмотрели и отвергли. Scout не будет поднимать inbox по ним, но **следующий** новый коммит — снова подхватит |
| **Пауза до события** | `watch_paused_until: "2026-09-01"` \| `watch_paused_until: "v3.0"` \| `watch_paused_until: "breaking_change_resolved"` | Временно не трогаем. Scout игнорирует апдейты до даты/версии/явного снятия паузы |
| **Полная заморозка** | `watch: false` + обязательный `notes: "причина"` | Отношения с апстримом закрыты. Живём своей жизнью |

**Правило:** любой отказ требует причины в `decline_reasons` или `notes`. Иначе через год запись выглядит как «забыли». История отказов — это наш архив продуктовых решений.

**Что делать при `update_available`, которое не берём:**
1. В `/update-library` помечаем «отклонить»
2. SHA добавляется в `declined_commits`, причина — в `decline_reasons`
3. Inbox-файл удаляется
4. Запись в `docs/memory/lessons/` если отказ поучительный

## Классификация апстрим-изменений

Scout при обнаружении обновления определяет тип и выставляет статус в inbox. **Логика классификации зависит от `adoption_type`:**

### Для `fork`

| Тип | Признаки | Статус в inbox | Действие человека |
|---|---|---|---|
| **patch** | Typo, refactor, docs-only, semver patch | `patch_auto` | Scout сам обновляет `source_commit` + `last_checked`; ревью не требуется |
| **minor** | Новая опция/метод, обратно совместимо | `update_available` | Ручное ревью: применить diff / отложить / отказать |
| **major** | Breaking change, переименования, смена концепции | `breaking_change` | Обязательное ревью + запись в `docs/memory/decisions/` |

Inbox-файл содержит **готовый diff** для применения.

### Для `reimplement`

| Тип | Признаки | Статус в inbox | Действие человека |
|---|---|---|---|
| **patch** | Мелочи в апстриме, ничего концептуального | `patch_auto` | Scout только обновляет `last_upstream_commit` + `last_checked`. Наш код не трогаем |
| **minor** | Новая фича в апстриме | `reimplement_candidate` | Ручное ревью: «нужно ли нам это? если да — переписать **нашу** реализацию вручную». Diff апстрима — как источник идей, не как патч |
| **major** | Концептуальная переделка в апстриме | `reimplement_review` | Обязательное ревью: пересматриваем нашу архитектуру с нуля в свете апстрима |

Inbox-файл содержит **сводку изменений и ссылки**, не diff для применения.

### Для `dependency`

| Тип | Статус в inbox | Действие |
|---|---|---|
| patch / minor | `dependency_update` | Обновить версию в `package.json` / `requirements.txt`, прогнать тесты |
| major | `dependency_breaking` | Ревью: читаем релиз-нотес, обновляем код под новый API, запись в `docs/memory/decisions/` |

**Эвристики classification** (без semver):
- ±5 строк, нет изменения сигнатур → patch
- Новые публичные сигнатуры, но старые остались → minor
- Удаление/переименование публичных сигнатур, слова `BREAKING`/`DEPRECATED` в коммите → major

## Лицензии и ledger

Поле `license` обязательно. Если апстрим сменил лицензию при обновлении — это всегда `breaking_change`, даже если код совместим.

| Лицензия | Можно держать в ledger | Ограничение |
|---|---|---|
| MIT / Apache 2.0 / BSD | Да | Указать attribution в коде/SKILL.md |
| LGPL | Да | Только как зависимость, не fork |
| GPL | Да | Только clean-room, `kind: pattern` |
| Proprietary / Unknown | Да с пометкой, но только `kind: pattern` | Никакого кода |

## Связка со скилами

| Скил | Обязанность по ledger |
|---|---|
| `/update-library` | При приёме находки из inbox — создать/обновить запись в ledger |
| `/analyze-and-adopt` | При заимствовании фичи — создать запись в ledger в конце Фазы 5 |
| `/generate-project` | При копировании скила в проектный пакет — инкрементировать поле `used_in_projects` |
| `/create-skill` (если на основе внешнего) | Создать запись с `kind: skill`, `watch: true` |

**Правило:** скил не считается завершённым, если запись в ledger не создана/не обновлена.

---

## Связка со Scout

Scout запускается в трёх режимах, см. `SCOUT_CONTRACT.md`:

1. **on-demand** — не трогает ledger
2. **background scan** — не трогает ledger, пишет в inbox (новое)
3. **watch** (новое) — читает ledger, проверяет апстрим записей с `watch: true`, пишет в inbox обновления

Watch-режим **только читает** ledger. Писать в ledger может только человек через скилы. Это граница ответственности: автомат не принимает решение о заимствовании.

## Жизненный цикл записи

```
  обнаружено в inbox                      найдено в коде без записи
         │                                        │
         ▼                                        ▼
  /update-library: решение         /analyze-and-adopt / аудит
         │                                        │
         └────────────── создать запись ──────────┘
                              │
                              ▼
                    watch: true? ──нет──▶ frozen (конец)
                              │
                             да
                              ▼
              Scout scan_watch находит upstream-изменения
                              │
                              ▼
            inbox(update_available | breaking_change | patch_auto)
                              │
                              ▼
              /update-library: решение (обновлять / отложить / заморозить)
                              │
                              ▼
                    обновить source_commit, last_checked
                              │
                              └──────▶ цикл
```

## Ретрофит (что делать с уже заимствованным без записи)

1. Пройтись по `_library/skills/` — каждый скил с внешним источником → запись в ledger
2. Пройтись по `_library/prompts/` — то же самое
3. Пройтись по `_library/mcp_catalog/` — то же
4. Что не удалось атрибутировать → `watch: false`, `source_url: unknown`, в комментарии «ретрофит, источник утерян»

Делается один раз при внедрении политики, потом ledger ведётся непрерывно.
