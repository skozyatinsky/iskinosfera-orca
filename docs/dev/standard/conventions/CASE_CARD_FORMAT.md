# CASE_CARD_FORMAT — стандарт карточки продукта/кейса

> Единый формат, в котором каждый проект описывает себя для внешнего мира:
> сайта-портфолио, презентаций, питч-доков, каталога продуктов.
>
> **SSOT — внутри проекта.** Карточка лежит в `<project>/docs/marketing/case-card.md`
> и едет вместе с кодом в git. Сайт-каталог собирает раздел «Наши работы»,
> читая карточки из всех подключённых проектов.

---

## 1. Зачем нужен этот стандарт

- Один источник правды о продукте — внутри его репозитория.
- Сайт не дублирует знания, а собирает раздел кейсов автоматически.
- Меняется фича — меняется карточка в том же PR — на сайте автоматически свежо.
- Из одной карточки собираются: страница продукта, превью в каталоге, PDF-питч,
  презентация, текст для WhatsApp/Telegram, OG-картинка.

## 2. Где лежит

```
<project>/
  docs/
    marketing/
      case-card.md          ← главный файл (этот стандарт)
      landing-sections.md   ← расширенные текстовые блоки для лендинга
      screenshots-plan.md   ← план съёмки скриншотов
      seo.md                ← SEO-метаданные
      screenshots/          ← готовые скриншоты (после съёмки)
        01-search.png
        ...
```

Карточку генерирует и поддерживает скил `product-page` (см. `_library/skills/product-page/`).

## 3. Структура файла

`case-card.md` — markdown с обязательным YAML-frontmatter и фиксированным набором секций.

### 3.1 Frontmatter (обязательный)

```yaml
---
# Идентификация
slug: rag-tender-system           # URL-safe, уникальный среди всех проектов компании
name: "RAG для тендерной документации"
short_name: "Тендер-RAG"          # для каталога/превью, до 25 символов
tagline: "Поиск ответов в комплектах тендерной документации за секунды"  # до 80 символов

# Классификация
kind: product                     # product | case-study | pattern
                                  #   product     — продаваемая коробка с собственной воронкой
                                  #   case-study  — история одного внедрения
                                  #   pattern     — повторяемое решение/услуга, продаваемая проектами
category: ai-platform             # ai-platform | service-desk | automation | website | mobile | other
status: production                # concept | mvp | beta | production | sunset
maturity_level: 4                 # 1=concept, 2=mvp, 3=beta, 4=production, 5=mature
year_started: 2025
year_current: 2026

# Принадлежность
owner: "ИнтроСофт"                # компания-владелец
client_type: internal             # internal | b2b | b2c | mixed
clients_public:                   # публично называемые клиенты (если есть согласие)
  - null                          # null = без публичного раскрытия

# Кейсы внедрений (для kind: product/pattern)
# Каждая запись — компактное описание применения. Если кейс вырастает,
# можно завести отдельную карточку с kind: case-study и сослаться через case_url.
deployments:
  - name: "Имя клиента или null"
    role: "встройка в портал стороннего продукта"   # короткая фраза-роль
    summary: |
      1-2 предложения: что сделали, на каком стенде, какой эффект.
      Без громких заявлений; только то, что подтверждается артефактами.
    year: 2025
    public_name_allowed: true
    case_url: null                # null = живёт записью внутри карточки;
                                  # URL = есть отдельная длинная страница (kind: case-study)

# Целевая аудитория (ICP)
target_audience:
  - "Тендерные отделы B2B-компаний"
  - "Госзакупочные подразделения"
  - "Корпоративные службы знаний"

# Технологии (для технического тэга)
tech_stack:
  - Python 3.12
  - FastAPI
  - FAISS
  - Ollama
  - Qwen3-14B

# Деплоймент
deployment:
  - on-premise
  - air-gapped                    # on-premise | air-gapped | cloud | hybrid

# Лицензирование (для внутренней витрины)
licensing: license-hub            # open | proprietary | license-hub | bundled

# Артефакты
hero_image: screenshots/00-hero.png
cover_image: screenshots/cover-1200x630.png   # 1200×630 для OG и каталога
demo_url: null                    # URL песочницы или null
case_url: /cases/rag-tender-system  # путь на сайте после публикации
repo_url: null                    # ссылка на репо (обычно null для proprietary)

# Метаданные
last_updated: 2026-05-06          # ISO-дата последнего обновления карточки
language: ru                      # язык карточки (ru | en | ...)
related_products:                 # slug'и связанных продуктов
  - service-desk-ai
  - rsd-rag-service
---
```

### 3.2 Тело карточки (фиксированные секции)

```markdown
# {{ name }}

## Проблема

(2–4 предложения. Конкретная боль конкретной аудитории. Без воды.
 Цифры, если есть. Что страдает сейчас.)

## Решение

(2–4 предложения. Что делает продукт, как именно решает боль.
 Не рекламно. Глаголы действия, а не «уникальный/инновационный».)

## Ключевые возможности

- **{{ feature_name }}** — {{ короткое объяснение, что и зачем }}
- ... (5–8 пунктов, не больше)

## Архитектура (1 абзац)

(Как устроено внутри. Уровень — для технического читателя, без полного дайва.
 Что и почему выбрали. 3–5 предложений.)

## Результаты / эффект

- {{ метрика, цифра, факт }} — например: «Время поиска по комплекту тендерной
  документации в 50 МБ: с 2–3 часов ручного чтения до 8–15 секунд»
- ... (3–5 пунктов; если нет цифр — конкретные качественные эффекты)

## Use cases

### {{ Сценарий 1 }}
(1–2 предложения о конкретной ситуации применения)

### {{ Сценарий 2 }}
...

## Кейсы внедрений (опц., для kind: product)

Раскрывается из frontmatter `deployments[]`. Для каждой записи:

### {{ deployment.name }}
{{ deployment.summary }}

— Год: {{ deployment.year }}
— Роль продукта: {{ deployment.role }}
— Подробнее: ссылка на отдельный case-study, если есть

## Чем отличается

(От чего конкретно отличается на рынке. 2–4 пункта.
 Не «лучше всех», а «делаем X там, где другие делают Y, потому что Z».)

## Стек и интеграции

(Раскрытие frontmatter `tech_stack` для тех, кому интересны детали:
 что почему выбрано, какие интеграции есть.)

## Ссылки

- Документация: ...
- Кейс полный: ...
- Контакт по продукту: ...
```

## 4. Правила содержания

### 4.1 Тон и стиль
- Любая карточка прогоняется через `humanizer` или `the-humanizer` перед публикацией.
- Если продукт принадлежит ИнтроСофту — применять `brand-voice` (skill).
- **Запрещено** в текстах: «уникальный», «инновационный», «революционный»,
  «лидер рынка», «не имеющий аналогов», «передовые технологии», «синергия».
- **Обязательно**: глаголы действия, конкретные цифры, имена технологий.

### 4.2 Цифры
- Если есть метрика — ставим. Если нет — не выдумываем.
- Цифры должны иметь источник в самом проекте (бенчмарк, измерение, кейс).
- Указывать единицу и условие: «1000 запросов/мин при p95=200мс на 1×RTX 4090».

### 4.3 Скриншоты (упоминание в карточке)
- В карточке — только `hero_image` и `cover_image` через frontmatter.
- Полный план съёмки + остальные скриншоты — в `screenshots-plan.md`.

### 4.4 Конфиденциальность
- Имена клиентов — только с согласия. Иначе `null` или категория («крупный
  ритейлер»).
- Не публиковать в карточке: внутренние URL, реальные креды, имена сотрудников
  без согласия, фрагменты production-данных.

## 5. Жизненный цикл карточки

| Когда | Что делать |
|-------|-----------|
| Создание проекта (`/generate-project`) | Скил `product-page` создаёт скелет карточки |
| Завершение модуля (`/finish-module`) | Перепроверить `Ключевые возможности` и `Результаты` |
| Релиз | Обновить `last_updated`, при необходимости пересобрать скриншоты |
| Изменение позиционирования | Обновить `tagline`, `target_audience`, `Проблема/Решение` |
| Sunset | `status: sunset`, `case_url` оставить (история продукта) |

## 6. Валидация

Файл проходит проверку:
1. YAML-frontmatter валиден.
2. Все обязательные поля заполнены (см. §3.1, не `TODO`).
3. Все фиксированные секции тела присутствуют (см. §3.2).
4. `slug` уникален в рамках компании (проверяется при публикации сайта).
5. `cover_image`, `hero_image` существуют как файлы (если не `null`).

Скрипт-валидатор: `_library/skills/product-page/scripts/validate_case_card.py`
(добавится при первой реализации).

## 7. Сборка раздела «Наши работы» сайта

Сайт-каталог получает на вход список проектов и для каждого:
1. Читает `<project>/docs/marketing/case-card.md`.
2. Парсит frontmatter — данные для превью (карточка в каталоге, фильтры).
3. Парсит тело — данные для страницы продукта.
4. Подгружает скриншоты из `<project>/docs/marketing/screenshots/`.
5. Применяет шаблон страницы продукта (см. `_library/skills/product-page/STRUCTURE.md`).

Это даёт автогенерацию каталога без CMS.
