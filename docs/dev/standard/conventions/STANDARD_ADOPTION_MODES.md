# Режимы раскатки стандарта

> Как стандарт Архитектора попадает в проект: три режима, правило выбора
> между ними и правило записи путей.
>
> Читается вместе с `FILE_AND_FOLDER_STANDARD.md` и
> `DOCUMENTATION_STANDARD.md`. Режим проекта объявлен в
> `docs/registry/architect_observed_projects.json`, поле `standard_adoption`.

---

## 1. Из чего состоит стандарт

Различать три части, иначе разговор о цене режима сбивается:

| Часть | Что это | Объём |
|-------|---------|-------|
| Документы-конвенции | `_library/agent_configs/global/*.md` плюс три документа, объявленных поимённо в `tools/sync_standard.py` | 18 файлов, ~296 КБ |
| Проверяющий инструмент | каталоги `tools/` и `schemas/` пакета | 181 файл, ~2,3 МБ |
| Выпускаемый пакет | `agent_project_standard` целиком: правила, инструменты, тесты, примеры, эталонный проект | 711 файлов, ~18 МБ |

`validate_structure.py` — не самостоятельный скрипт: он импортирует соседние
модули пакета (`v128_validation`, `tz_governance`, `rule_traceability_types`),
поэтому едет весь `tools/` целиком, а не один файл. Каталог `reference/`
(10 МБ) в проект не едет: проверка профиля `target-project` его не читает —
проверено прогоном точного набора флагов из сборки RAG по усечённому дереву.

Проекту для работы нужны первые две части. Третья нужна тому, кто пакет
сопровождает или отдаёт клиенту как документацию.

## 2. Три режима

### `reference` — только ссылки

В проекте лежит `.claude/imports.yaml` с перечнем документов Архитектора.
Агент читает их напрямую с диска Архитектора в момент работы.

Работает, только пока Архитектор лежит на том же диске по тому самому пути.
Ни в сборке CI, ни на другой машине, ни у второго участника этого нет.

Применим к проекту, у которого нет блокирующей проверки и который правится
только рядом с Архитектором.

### `tool_pinned` — закреплённый инструмент

В проект едут документы-конвенции, каталоги `tools/` и `schemas/` и номер
версии — 202 файла, ~2,6 МБ. Остальной пакет не едет: ни примеры, ни
тесты, ни эталонный проект, ни `reference/`.

Проверка выполняется в самом проекте, без Архитектора. Путей к чужому диску
не требуется вовсе. Версия известна, значит `/sync-standards` есть что
обновлять.

Режим по умолчанию для всех проектов с блокирующей проверкой.

### `full_copy` — полная копия пакета

В проект едет весь выпускаемый пакет, в `docs/dev/agent_project_standard/`.

Нужен там, где пакет сам является предметом работы: у Архитектора — для
проверки самого себя, у проекта, отдающего стандарт клиенту как часть
документации.

Цена — сотни файлов при каждом обновлении версии.

## 3. Правило выбора

> Проверяющий инструмент едет вместе со своей версией. Если у проекта есть
> проверка, которая должна отработать там, где Архитектора нет на диске, —
> режим не `reference`. По умолчанию это `tool_pinned`; `full_copy` — только
> если проекту нужен сам пакет, а не проверка.

Машинный признак: вызов валидатора в `.github/workflows/`. Есть вызов —
`reference` неприменим.

Признак снимает `tools/standard_adoption_facts.py` — одна реализация на всех:
её зовёт шаг 2.1 скила `/onboard-project` и тест
`tests/test_standard_adoption_mode.py`. Вторая копия правила расходится с
первой молча, и тогда проверка проверяет копию, а работает оригинал.

```bash
python3 tools/standard_adoption_facts.py --project <путь>   # факты по проекту
python3 tools/standard_adoption_facts.py --registry         # сверить весь парк
```

Объявленный в реестре режим сверяется с **веткой парка** — `origin/main`, а
у репозитория без удалённого с местной `main`. Рабочее дерево источником не
служит: оно показывает чекаут одного разработчика. После влития переноса
шесть проектов держали стандарт на `origin/main`, а в рабочих копиях стояли
на своих ветках без него — сверка по дереву объявила бы режим неразвёрнутым
у всех шести.

Режим обязан быть разрешён признаком и обязан существовать (`full_copy` →
каталог пакета, `tool_pinned` → `docs/dev/standard/`). Осознанно отложенный
перенос объявляется полем `standard_adoption_pending` записи проекта — цель,
причина с фактом, дата, ссылка на задание.

Отсрочка покрывает **нарушение**, а не намерение. Если объявленное совпадает
с фактом, отсрочке нечего покрывать, и запись роняет проверку — так же, как
пережившая перенос. Готовая, но не влитая ветка — это заметка в `notes`, а не
долг перед правилом.

Признаки, которые правилом **не** являются: модель поставки (клиентский,
`server-on-premise`, `saas-hosted`), дата подключения проекта, решение
отдельной сессии. Проверка живёт в разработке и клиенту не уезжает.

## 4. Правило записи путей

Абсолютный путь к Архитектору в файл проекта не записывается. Он машинно
зависим: на Mac и на Windows он разный, а в сборке CI его нет вовсе.

- Во время работы путь к Архитектору не нужен ни одному режиму, кроме
  `reference`. Это и есть довод против `reference`.
- Во время синхронизации (`/sync-standards`, `/onboard-project`) путь берётся
  из переменной окружения `ARCHITECT_ROOT`. Значения по умолчанию у неё нет:
  подстановка чужого домашнего каталога маскирует ненастроенное окружение
  ошибкой «файл не найден».
- В документации пишется имя переменной, а не значение — так же, как
  `PROJECTS_ROOT` в реестре проектов и `OBSIDIAN_VAULT` в `CLAUDE.md`.

## 5. Что записано в манифесте проекта

`.claude/imports.yaml` при `tool_pinned` и `full_copy` описывает, что уже
скопировано, а не куда сходить:

- `standard_version` — версия, из которой скопировано;
- `source_commit` для каждой записи — коммит Архитектора на момент копирования;
- `local_path` — путь внутри проекта, который обязан существовать.

Поле `architect_root` в манифесте не хранится. Объявленный `local_path`,
которого нет на диске, — нарушение: манифест обязан описывать положение дел,
а не намерение.
